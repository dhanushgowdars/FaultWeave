# Phase 16F — grounded incident-investigation assistant

Phase 16F adds an optional, read-only explanation layer over the frozen Phase
16E evidence contract. It is not a transaction agent, fault controller or
automatic remediation system.

## Public API

`POST /api/v1/transfers/{transfer_id}/assistant/explain`

The authenticated owner or an engineer can request one of five bounded focuses:
`overview`, `first_failure`, `funds`, `recovery` or `model`. A short optional
question is treated as untrusted data. Unknown fields and questions longer than
400 characters are rejected.

The response separates:

- `observed_fact` — persisted workflow or journal evidence with event IDs;
- `model_prediction` — independently correlated frozen-model output;
- `ai_inference` — a probable explanation, never represented as confirmed fact;
- `unconfirmed` — information the available evidence cannot establish.

Every cited event ID must exist in the case evidence index. Invalid JSON,
invented citations, provider failures, timeouts and quota failures are rejected
and replaced by an explicitly labelled deterministic evidence explanation. The
fallback never labels its rule-based probable-cause assessment as AI inference.

## Privacy and safety boundary

Only the normalized, case-scoped Phase 16E evidence contract is accepted.
Before an optional provider call, FaultWeave removes or aliases account numbers,
idempotency keys, user/reviewer identity, correlation IDs, authorization values,
tokens and credential-shaped text. Log text that resembles prompt injection is
replaced before prompt construction.

The assistant cannot:

- create or retry a transfer;
- activate or remove a fault;
- approve or resume a review case;
- update PostgreSQL or the ledger;
- override workflow, journal or frozen-model results;
- access protected fault ground truth.

The API key exists only in the gateway environment. It is never returned by an
API and must never be placed in the frontend bundle or Git history.

## Groq provider

Phase 16F has one generative provider: Groq Chat Completions with strict JSON
Schema output. The selected model is OpenAI's open-weight GPT-OSS 120B served by
Groq; this is not the separately billed OpenAI API. Configuration is server-side:

```text
FAULTWEAVE_ASSISTANT_ENABLED=true
FAULTWEAVE_ASSISTANT_PROVIDER=groq
FAULTWEAVE_ASSISTANT_MODEL=openai/gpt-oss-120b
GROQ_API_KEY=<private key>
FAULTWEAVE_ASSISTANT_TIMEOUT_SECONDS=8
FAULTWEAVE_ASSISTANT_MAX_ATTEMPTS=3
FAULTWEAVE_ASSISTANT_RETRY_BASE_SECONDS=1
```

Transient `429` and `5xx` responses use bounded exponential backoff (three
attempts by default, capped at eight seconds and honoring a numeric
`Retry-After` header). Groq's specific `json_validate_failed` generation error
is also retried; unrelated `4xx` responses remain permanent. The adapter uses
low reasoning effort and a bounded completion budget. It sends Groq only the
strict structural schema plus the non-empty-array requirement, then enforces
the complete Pydantic length constraints locally after generation. If a
schema-valid provider response still violates the local safety contract,
FaultWeave makes one bounded correction attempt with no additional evidence.
Provider-generated factual statements are structurally required to contain at
least one event citation, and entries in `observed_facts` are constrained to the
`observed_fact` kind. The provider schema limits citation values to event IDs
from the selected case only. Citation IDs are still checked against the
case-specific evidence index after generation; schema compliance alone is
never trusted.
If all attempts fail, FaultWeave returns the
deterministic evidence explanation; transaction and evidence APIs never depend
on provider availability.

The safe default is `FAULTWEAVE_ASSISTANT_ENABLED=false`. Without a key—or when
Groq is unavailable—the same endpoint returns a complete
`DETERMINISTIC_FALLBACK` response whose status and provenance make clear that it
was not generated by AI. Therefore provider availability is never a dependency
of transfer processing or evidence inspection.

## Acceptance gate

Unit and API tests cover strict schema enforcement, input bounds, secret
minimization, prompt injection, hallucinated citations, retry and fallback
behavior, caching and authentication. The live verifier creates a real durable
transfer, requires an `AI_GENERATED` result from Groq GPT-OSS 120B, calls the
assistant twice, verifies cache use and citation integrity, proves
cross-customer denial, and requires the evidence export to remain byte-for-byte
unchanged.
